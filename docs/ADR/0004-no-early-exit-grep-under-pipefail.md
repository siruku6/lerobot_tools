# 0004: 出力の長いコマンドを `grep -q` にパイプしない

## 背景

step スクリプト（`envs/` 配下の、docker build 中に 1 つの工程を実行するシェルスクリプト群）は
すべて `set -euo pipefail` で始まる。`pipefail` は、パイプでつないだコマンドのうち
**1 つでも失敗したら、パイプライン全体を失敗とみなす**シェルのオプションである。

ここに次のような書き方を混ぜると、**条件判定が実行のたびにランダムに反転する。**

```sh
if ! ldconfig -p | grep -q "$SONAME"; then   # 危険
```

`grep -q` は最初の一致を見つけた時点で即座に終了する。そのとき `ldconfig -p` がまだ
出力を書いている途中だと、書き込み先のパイプが既に閉じているため、`ldconfig` は
SIGPIPE を受けて終了コード 141 で死ぬ。`pipefail` がその 141 をパイプライン全体の
結果にするので、**探しているライブラリが実際には登録されているのに「無い」と判定される。**

出力が長いコマンドほど、`grep -q` が先に抜ける確率が上がる。`ldconfig -p` は
1000 行規模になるため、このホストでの実測（2026-09-21）では **300 回中 184 回が 141** だった。

実際に起きたこと:

- `register_npp.sh`（torchcodec が要求する NPP ライブラリを動的リンカに登録する step）の
  事後条件がこの書き方だった。`ldconfig -p` の出力に `libnppicc.so.12` が出ているにもかかわらず
  「登録後も見えない」と報告して docker build が失敗した。
- 発生が確率的なため、原因が分からないまま「RUN を分けたら直った」ように見えた時期があった。
  実際には分けたことでタイミングが変わり、当たりを引いただけだった。
  同じ構成で後日ビルドしたところ、`train` は通って `datagen` だけが落ちるという形で再発した。

**この失敗の厄介さは、コードを読んでも間違いに見えない点にある。** ライブラリは本当に登録されており、
`ldconfig -p` の出力も正しい。診断出力を仕込んで初めて「判定だけがおかしい」と分かった。

## 決定

`envs/common/lib/guard.sh` に `ldconfig_has <名前>` を置き、step からはこれを呼ぶ。
この関数は `ldconfig -p` の出力をいったん変数に受け取ってから、シェルのパターンマッチで
照合する。**パイプそのものが無くなるので、SIGPIPE が起こりえない。**

```sh
ldconfig_has() {
    _ld="$(ldconfig -p 2>/dev/null || true)"
    case "$_ld" in (*"$1"*) return 0 ;; (*) return 1 ;; esac
}
```

一般則として、`set -o pipefail` の下では **出力を最後まで読まないコマンド**
（`grep -q`、`grep -m N`、`head -n N`）に、出力の長いコマンドをパイプでつながない。
必要なら上記のように出力を変数へ受ける。

逆に、`grep -c`・`grep -o`・`sort`・`wc` のように**入力を最後まで読むコマンド**は
パイプの右側に置いてよい。これらは書き手側を待たせないので SIGPIPE を起こさない。

## 影響

- ライブラリの有無を調べる判定が決定的になる。同じ入力なら必ず同じ結果になる。
  検証として `ldconfig_has libc.so.6` を 300 回呼び、300 回とも一致する（取りこぼしゼロ）ことを確認した。
- `ldconfig -p` の出力全体をメモリに載せるため、`grep -q` よりわずかに無駄が増える。
  数百 KB 程度であり、docker build の中では無視できる。
- この規則は `ldconfig` に限らない。今後 step の中で出力の長いコマンドを判定に使うときは、
  同じ理由で同じ形にする必要がある。
