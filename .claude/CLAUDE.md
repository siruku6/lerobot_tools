## 1. これは何のためのファイルか

以前、別の Claude セッションが書いたコメントを人間と一緒に読み直したとき、
「出力」「状態を持たない」「採点イメージ」「移行元のリポジトリ」といった言葉が、そのファイル単体は
もちろんリポジトリ全体を見ても定義されておらず、別の Claude セッションにもプロジェクトのユーザにも
分からなくなっていた。**Claude 同士であっても、セッションをまたぐと文脈は一切引き継がれない。**

このファイルは、次にこのリポジトリを触るセッション（人間・Claude を問わない）が同じ状況に陥らないための、
文書・コメント・チャットでの会話の書き方の規則である。

## 2. 文書・コメントを書くときの原則

### 2.1 そのファイル単体で伝わるように書く

コード中のコメントやドキュメントは、**他のファイルを一切見ずに、そのファイルだけを
読んで、大体何を言っているかが分かるように書く。** 「他のファイルに書いてあるから、このファイルには
書かない」という考え方は、コード（DRY）には当てはまっても、ドキュメントやコメントには当てはまらない。

- NG: `# 出力の型を揃えるためだけの関数群。`
  （「出力」が何の出力かが、このファイルだけでは分からない）
- OK: `# docker build 実行時に各stepスクリプトが標準出力へ出すログの見た目を揃えるための関数群。`

**既存の文章を他のファイルへ移す・コピーするときも、同じ基準で再確認する。** 元のファイルでは
前後の文脈があって意味が通っていた一文でも、移動先ではその文脈が無く、唐突な用語になることがある。
「前から書いてあった文章だから」を理由に自己完結性のチェックを省略しない。

### 2.2 書く前に裏取りする。裏取りできないことは断定しない

コメントに書く「なぜ」は、実際にコードを読む・grep する・（可能なら）手元で再現して確認してから書く。
記憶や推測をそのまま事実のように書かない。

- 裏取りの例: `clone --depth 1 は ref しか受け付けない` という主張は、実際に
  `git clone --depth 1 --branch <commit hash>` を試して失敗することを確認してから書いた。
- 裏取りできない場合は、断定せずにそう書く。書いた人（多くの場合ユーザー）に確認する。
  例: `versions.env` の `LEROBOT_TAG` は「評価用は 0.4.4 が必要（理由不明）」とだけ書いてあり、
  推測で理由を埋めていない。

### 2.3 経緯・背景は書かない。重要なものだけ ADR に切り出す

設定ファイルやコードのコメントに、変更の経緯・背景・検討の過程を長々と書かない。文量が増え、
本来知りたい「今の値・今の動作」が埋もれる。

- 経緯が一般的・自明な理由（例:「ブランチ先端は更新されうるのでコミットで固定する」）であれば、
  コメントごと削除してよい。
- 破ると**サイレントに壊れる**・過去に実際の事故につながった、といった重要な経緯であれば、
  `docs/ADR/NNNN-短い説明.md` として**1トピック1ファイル**で切り出し、元の場所には
  1行のポインタだけ残す（書き方は [4. ADR の書き方](#4-adr-の書き方) 参照）。

### 2.4 用語は初出で定義する。表記も統一する

プロジェクト固有の用語や省略語（例:「採点イメージ」「pin」「ref」）は、そのファイルの中で最初に
使う場所で一言定義してから使う。また同じ概念には同じ言葉を使う。

**「一般に広く知られた用語」と「このプロジェクト・このファイル固有の意味を持つ言葉」を区別する。**
前者（例: venv、docker、git、pip）は読者が知っている前提でよく、説明は不要。後者は、たとえ
見た目が一般的な単語・よくあるファイル名（例:「config.yaml」）であっても、**それがこのリポジトリの
中で何の役割を持つか・なぜ話題に上っているか**は説明が要る。「一般的な言葉に見えるから説明不要」と
判断しない。迷ったら、そのファイルの初見の読者が「これは何？」と聞き返すかどうかで判断する。

- 例: 「版」は意味が曖昧（版=edition なのか version なのか判別しづらい）なため、
  このリポジトリでは「バージョン」に統一した。
- 例: シェルの `source`（`. file`）コマンドは、読み手がシェルに詳しいとは限らないため、
  「別プロセスを起こさず、指定したファイルの中身をいま実行中のシェルにそのまま読み込んで実行する」
  のように、初出時に平易な言葉で説明する。
- 例: 「venv」自体は一般用語なので説明不要。しかし「LIBERO の設定（`config.yaml`）」は
  一般的なファイル名に見えても、このリポジトリ固有の役割（LIBERO が起動時に読み込むパス一覧の
  設定ファイルであること）を説明しないと、読者には何の話か分からない。

### 2.5 ファイル冒頭・docstring の一文目は、具体例より一段抽象化する

ファイルの冒頭コメントや、関数・メソッドの docstring の**一文目**は、そのファイル・関数が
扱う具体的な対象を並べるだけで終わらせず、それらに共通する役割・カテゴリを一段抽象化して書く。
具体例は、その一文の後に（括弧や次の行で）補足として残す。抽象化と具体例のどちらか一方だけでは
足りない。抽象化だけでは中身が分からず、具体例の列挙だけでは全体像がつかめない。

抽象化の見つけ方: 並んでいる具体例が一見バラバラに見えるときほど、「これらは何のために・
どういう共通の役割で存在するか」を自問する。

- NG: `# mujoco / robosuite の描画と、LIBERO-plus のモーションブラー処理に要る、`
      `# pip では入らない共有ライブラリを OS に入れる step。`
  （「描画」と「モーションブラー処理」が一見別々の話に見え、両者に共通する役割が
  一文目だけでは伝わらない）
- OK: `# シミュレーションの観測画像を生成・加工する処理に必要な共有ライブラリをOSに install するための script`
      `# 各共有ライブラリは mujoco/robosuiteの描画、LIBERO-plusのモーションブラー処理で用いる`
  （「観測画像の生成・加工」という一段抽象化した役割を先に示し、具体例を続けている）

## 3. チャットでの会話にも同じ原則を適用する

ここまでの原則は、書き残す文書だけでなく、**ユーザーとのやり取りそのもの**にも適用する。

## 4. ADR の書き方

ADR（Architecture Decision Record）は、`docs/ADR/` 配下に**1つの決定ごとに1ファイル**で置く。
ファイル名は `docs/ADR/NNNN-短い説明.md`（例: [`docs/ADR/0001-torch-stack-pinning.md`](docs/ADR/0001-torch-stack-pinning.md)）。

各ファイルは次の3セクションで書く。

| セクション | 書く内容 |
|---|---|
| 背景 | なぜこの決定が必要だったか。破るとどう壊れるか（サイレントに壊れる場合は特に明記する） |
| 決定 | 実際に何を決めたか。具体的な設定・変数名で書く |
| 影響 | この決定によって、今後何がしやすくなり、何がしにくくなるか（良い面・悪い面の両方） |

新しく ADR が必要かどうかは [2.3](#23-経緯背景は書かない重要なものだけ-adr-に切り出す) の基準で判断する。
